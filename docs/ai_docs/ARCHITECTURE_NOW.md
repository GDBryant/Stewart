Product version 3.0.14 — source of truth is `hosts/vscode/package.json` `version`; `build.gradle.kts` parses it as the plugin-version fallback, `modules/kernel/src/version.ts` `STEWART_VERSION` mirrors it for runtime use, and `pnpm check:docs` fails on drift (also against the `ARCHITECTURE_DIAGRAM.md` `(vX.Y.Z)` line); `pnpm version:set <x.y.z>` (`scripts/sync-version.mjs`) updates all four sites at once. ## 3. Run paths

There is exactly one chat path: the lead session.

### 3a. Lead path

`handleChatSend` (no `/direct`, no orchestrated path, no classifier) first routes a leading `/` through `runSlash` (`@stewart/slash`: parser, `createSlashRegistry`/`runSlash`, built-ins in `commands/`; core builds one `createSlashRegistry()` — duplicate/alias names throw at construction, `find` matches name or alias case-insensitively, a command's thrown error is captured as `/<name> failed: <msg>` — and wires `SlashSessionPort {send, clear}` to `sessions.send`/`sessions.clear`): a registry of local commands (`/help` — list commands; `/init` — create `AGENTS.md` + `docs/ai_docs/` memory stubs (`ARCHITECTURE`, `COMMANDS`, `DECISIONS`, `PROGRESS`, `EVENTS`, `GOTCHAS`, `MEMORY`), then an `ask_user` card offers to send the project-analysis prompt; `/clear` — start a new conversation: `SessionService.clear(sessionId)` and `history.delete` (via `SessionService.delete`, which throws on refusal) share `dropSession` — refused while a turn is queued or running for the session, the history delete is enqueued on the session's turn chain so sends/resumes issued meanwhile queue behind it — deletes the history file (its `onDelete` hook also drops the engine/plan/turn/archive/child artifacts, the change tracker and the checkpoints), then emits `chat.cleared` with the sessionId (a deletion failure is reported back instead of a silent clear); `//` escapes to a literal leading slash). Slash output reaches the chat as `chat.local` events (protocol; the webview renders them as assistant items — never sent to a model, never persisted); unknown commands answer locally. Commands are discoverable via `slash.list` (core `handlers/slash.ts` → `slashRegistry.list()`; both hosts reply `slash.commands`; the webview caches them for composer autocomplete). Non-command input resolves the enabled `lead` role and calls `ProjectCtx.sessions.send`. `SessionService` (`@stewart/session`) loads the `ChatHistoryStore` transcript + `<stateDir>/sessions/<id>.engine.json`, appends the user message, resolves the lead's **eligible chain** — `eligibleChain` (roles-skills `chain.ts`): `role.chain` else `[role.agent]` else the lead's chain (for lead: the first agent); only agents `agentRefusal` accepts (current passing `qualified[kind]` record — `version < QUAL_MIN_VERSION` refuses "qualification out of date"; window ≥ `needs.minContext` from `contextTokens` or the record's verified `context` — an unknown window is refused "context window unknown"; vision when needed), in chain order; empty → failed "no qualified agent for role <id>: run Qualify in settings" — builds the system prompt (lead prompt + one-line skill index + `loadProjectContext` cut to 8000 chars) and tools (`projectTools(...).for(lead)` + `load_skill` + `ask_user` via `interaction.questionPrompt` + `delegate` + `health_report` + `set_check` + plan tools), then runs `engineFor(channel type)` — `claude-code` for `claude-cli` channels, `native-loop` for everything else. `maxTurns` = `settings.runTurnLimit` (default 60; settings tab "run turn limit"), which overrides `lead.turnBudget`; `turnsFor` (session `taskRun.ts`) makes any budget ≥ `UNBOUNDED_TURNS` (1000) unbounded (`Infinity`: native-loop runs until the model stops, adds no budget notes, and `claude-code` gets no `--max-turns`) — loop guard, cost cap and cancel still end a run; a role `turnBudget: unlimited` stays 200; a repair attempt is 1 turn.

The session emits `run.started`, `text_delta`/`reasoning_delta`, `tool.request`/`tool.outcome`, and `engine.context` for `claude-code` turns (roleId `lead`); approvals route through `policyApprove(lead, permissions.gate)` (`modules/session/src/policyApprove.ts`) — one `decide(role, actionOf(preview))` before the user-facing gate, so the same role policy applies under both engines — so `chat.approve`/`chat.answer` keep working; `permissions.bypass {projectId, on?} → {on}` sets/queries the per-project bypass mode (in memory: `Permissions.decide` returns `allow` before grant checks, no grants recorded, role policy still applies); usage meters into `RunLedger` (role `lead`) with `cost.summary` when cost > 0 and abort + failed "cost cap reached" past `costLimit.perRunUsd`. At turn start it takes a change-tracker baseline (`begin("turn-<runId>")`, persisted to `<stateDir>/sessions/<id>.turn` so `chat.revert` with `"turn"` restores it — the webview shows a "Revert this turn" action on a failed run's outcome line). After the engine stops it diffs that baseline, merges paths whose last write record succeeded into `changed` (the tracker misses nested git repos), and runs `runCheck` on `declaredCheck(set_check)` — failed last write records (`write_failed`; forgiven when the path is in `changed`, or the path does not exist and a later write record succeeded — a mistyped path the model then corrected), declared files that must exist, the commands in the task contract (`set_check({command, files?})` — approved at declaration; `.stewart/project.yaml` `verify:` argv lists — gated like any command and run only when the tracker diff is non-empty or unknown; must exit 0), empty reply — emits `check.result` (evidence details on the wire), and finishes `done` only when the engine stopped normally **and** the check passed; the lead's reply is not citation-checked (it may name files that do not exist yet). Each contract command runs once per attempt; the last attempt's check result is the result (`cancelled` on cancel, else `failed` with the engine error or failing check details). Stop (`chat.cancel` → `SessionService.cancel` → `RunState.controller.abort()`) shares one signal across the lead and all delegated children; `runTask` races `tracker.begin`/`diff` and the check against it (`abortRace` throws `AbortedRun` → `cancelled`), a verify is skipped entirely once aborted, and a thrown child run still emits `task.failed` — so a parked task unwinds instead of waiting out a stuck op, and `run.finished` settles any leftover pending/running task rows in the webview. `run.finished` on `done` and `failed` carries `outcome {changed: string[], verified: "command"\|"files"\|"none", command?, tracking?: "unavailable", trackingReason?}`; failed runs also carry `contextAtFailure: "<inputTokens>/<windowTokens>"` from the latest `engine.context` (the qualified agent window is the fallback when the CLI omits `modelUsage.contextWindow`) — `changed` is the tracker diff (shell-only edits count, in or out of git), `verified` names what confirmed the result (all contract commands ran and passed — `command` lists them joined with `; ` — else declared files present, else none); the webview shows it as one status line ("No files changed", "Changed N files, not verified", "Changed N files; verified: <command>", "Changed N files; required files present", or "File changes not tracked: <reason>"). Transcript + engine state persist incrementally (`stepSaver`, a single-flight coalescer): once right after the user message is appended (before the engine starts), once coalesced after every `tool.outcome`/`finished` engine event (`TaskSpec.onStep` — at most one save in flight, steps that arrive meanwhile coalesce into exactly one more save that reads the live transcript, so a post-compaction save can never be overwritten by pre-compaction state), and at task end/after each milestone. Save failures log and never fail the run. On load `closeOpenCalls` repairs a transcript interrupted mid tool batch (each unanswered call of the last open batch gets a `tool` message `Interrupted: the session ended before this call finished`); a trailing user message is left alone. Child transcripts persist the same way to `<stateDir>/sessions/<sessionId>/<taskId>.json`. `chat.cancel` → `sessions.cancel`. Turns on one session serialize.

**Escalation over the chain** (primary `agent` → optional `secondary`). Each attempt runs the next eligible agent. A failed attempt — check failure, engine error, `turn_limit`, `loop_guard` — escalates: a handover user message is appended (`Handover: the previous agent (<id>) did not finish this task. Goal: … Tried: … Failing evidence: … Continue from the current state of the files.`), `run.escalated {from,to,reason}` is emitted (reason `check_failed`|`error`|`turn_limit`|`loop_guard`|`loop_guard_divert`), and writes/changed-file records accumulate so the final check covers all attempts. "Tried" outcomes are matched to calls by `callId`. No escalation on cancel or cost cap. After the last agent fails the session asks via `ask_user`: when the last attempt ended `turn_limit` the question is "Ran out of turns (<latest attempt's maxTurns>) on <lastAgentId>. Continue with a fresh budget, reply with guidance, or stop." with options `["Continue", "Stop"]` (`Continue` appends a fixed continue-from-where-you-stopped instruction); otherwise "All agents for this task failed. … retry once more on <lastAgentId>, or stop." with options `["Stop"]`. The card also offers a free-text reply (typed text is the guidance): any other answer retries that agent once with the guidance appended, keeping the transcript; `Stop`/timeout fails with the evidence. Delegated children escalate along their own role chain identically but never ask the user — they return `status: failed` to the lead.

### 3b. Engines

`native-loop` (`engines/nativeLoop.ts`): per model turn `channel.chat` with native `tools` (no text shim), streams text/reasoning/usage, appends assistant/tool messages to the transcript, executes calls sequentially — consecutive calls on tools flagged `parallel: true` run concurrently via `Promise.all`, preserving tool-message order — (validate → preview → `approve` → 120 s timeout — skipped for `awaitsUser` tools (`ask_user`, `plan_write`) and `noTimeout` tools (`delegate`) — window-aware result cap (§3j E4), image results pushed as user image messages), emits `write` records for WriteFile/EditFile/ApplyPatch, finishes `stop`/`turn_limit`/`cancelled`/`error`/`loop_guard`. Turn budget (`budgetTurn`, only for `maxTurns >= 10`, so bench probes and conformance are untouched): a `[Stewart] 3 model turns left…` user note is appended before the third-to-last turn, and the last turn is report-only — a `[Stewart]` note asks for findings, changes and the exact remaining change and says tool calls are ignored. Tools stay in that request so the history is not flattened (`forNative`) and the cache prefix holds; any calls it still emits are dropped unrun (an empty reply becomes a `(No report…)` placeholder) and the run finishes `turn_limit`. Both notes stay in the transcript. `beforeModelTurn` (session: compaction) runs before every model request. `role.think` (optional; shipped `auditor` sets `false`) reaches the request as `think` (Ollama only; omitted when unset). Reasoning depth is separate from the switch: `effort` (`low|medium|high|max`; role override → agent value → `medium`, `effectiveEffort` in roles-skills) reaches the request as `effort` — **`think` is not redundant with `effort`**: `think === false` is the only hard off-switch and beats any effort, while `effort: high|max` turns Ollama `think` on only where `think` is unset (`low` is a no-op on Ollama, which has no granular budget); a length-truncation retry forces `think: false` and drops `effort` with it. Ollama `num_ctx` is sized prompt×1.25 + 4096 output tokens (a reasoning model spends thousands before answering). A reply cut off by the length limit (`done.truncated`) before any text or tool call is retried once by `modelTurn` with `think:false` and `minNumCtx` = 2× the tokens used (min 8192, capped by the model window); cut off again → `finished` error "reply cut off by the context window…" instead of a downstream "no json block". The loop guard (`engines/loopGuard.ts`, also used by `claude-code`) keeps only the last 12 recorded calls and clears the window on any successful file-write call, so long runs that legitimately re-read files do not trip; it trips when the same call (tool name + canonical JSON args) fails 3 times or returns the same result 3 times within the window, or after 6 consecutive model turns where every call failed or was invalid — the session treats it like `turn_limit` (escalates): first a **loop-guard divert** (session `divert.ts` `maybeDivert`, called from `taskRun.runChain`) switches once to the strongest reasoning-capable eligible agent — `divertTarget` (roles-skills `chain.ts`): the `settings.escalation.onLoopGuard.agent` id wins when eligible, else ranking reasoning-capable > unknown, wider context window, deeper effective effort (caps from the probe-merged config; cross-role agents eligible; the tripping agent and already-tried ids excluded); a divert target already pending in the chain is pulled to the front; the diverted attempt alone uses `escalation.onLoopGuard.effort` (else its effective effort) and the handover is emitted `run.escalated` with `reason: "loop_guard_divert"` (other handovers keep their static reason) — `escalation.onLoopGuard.enabled: false` (or nothing eligible) makes the divert a no-op and the static chain proceeds; absent `escalation` = auto-ranking; each run diverts at most once. The second identical call returns a `[Stewart] … do not repeat it …` warning that the native loop appends to the transcript as one user message. Foreign tool names (`Bash`/`Read`/`Write`/`Edit`/`Glob`/`Grep`) resolve to the matching built-in via `ToolRegistry.resolve` when the role has it and the mapped args validate; unknown top-level args on closed schemas are dropped with a note in the result; an unknown name lists the available tools.

`claude-code` (`engines/claudeCode.ts`/`claudeLines.ts`/`claudeContext.ts`/`claudePost.ts`) spawns the Claude Code CLI as a full agent in the project root: `claude -p --input-format stream-json --output-format stream-json --verbose --permission-prompt-tool stdio --include-partial-messages --model <normalizeModel(agent.model)>` plus `--append-system-prompt` (non-empty system only), `--max-turns`, `--effort <turn.effort>` (only when the effective effort is not the CLI default `medium`/unset **and** the channel reports `effortSupport` — `ManagedChannel.effortSupport(model)` reads merged `modelCaps`; engines never read raw caps), and `--resume <state.cliSessionId>` when stored. `effortSupport` is probed by the claude-cli adapter (`ClaudeCliAdapter.effortSupport`): `claude --help` runs once per CLI path (temp dir, `childEnv`, default 10 s timeout; `claudeProbe.ts`; definite results memoized in the adapter, unknown ones retried), reported in `probeCaps` and — when the caps carry no explicit value (e.g. after an IDE restart) — resolved at run start by `ManagedChannel.resolveEffortSupport` before argv is built; a logged-out or model-free CLI is a known "no" (`false`), spawn errors/timeouts leave it unknown (the flag is omitted). It uses the CLI's own tools — `turn.tools` is ignored — under `claudeChildEnv` (host env minus `ANTHROPIC_API_KEY`/`ANTHROPIC_AUTH_TOKEN`, `MCP_TOOL_TIMEOUT` defaulted to 6 h because Stewart's MCP tools wait on approvals, plan approval and child runs, plus `cfg.extraEnv`). The last user message goes to stdin as one stream-json line (images as base64 blocks); stdin stays open for control traffic, closed after `result`. `can_use_tool` control requests route through `turn.approve` (session-wrapped by `policyApprove`, so role policy applies to the claude-code lead and children alike — enforcement is only as good as the CLI sending `can_use_tool` for every mutating tool) with a mapped preview (meta `roleId` = `turn.roleId`). Every spawn carries `--setting-sources <cfg.settingSources>` (default `""`: no user/project/local settings are loaded, so user CLI `permissions.allow` rules cannot pre-approve a tool without a `can_use_tool` request — the trade-off is that user CLI settings such as hooks and env are not loaded unless the channel sets `settingSources`, which re-opens that pre-approval). Context sync: `state.cliSeen` counts transcript messages the CLI session has seen; at run start, messages before the final user message it has not seen (other-engine turns, handovers, or everything after a compaction) are prefixed to the user line as a `Earlier in this conversation (not yet seen by you):` recap (role-labelled, `[tool <name>]` calls, 300-char tool results, tail-biased 12k cap), and `cliSeen = transcript.length` after the run; the stale-`--resume` retry reuses the same recap. In reverse, the native loop's `forNative` flattens assistant messages containing calls to tools it lacks (other-engine calls) into plain text and drops their tool messages. `claudeCode.complete` spawns `claude -p --output-format json --tools "" --json-schema <schema>` — `structured_output` when present, else the `result` text parsed as JSON (one fenced block allowed), validated by the same `validateArgs`; `is_error` → not ok (Edit/Write/MultiEdit/NotebookEdit → file preview relativised to cwd, Bash → command, others → `OTHER`); other control subtypes get an error response. Deltas dedupe by `api_message_id`; `tool_use`/`tool_result` → `tool.request`/`tool.outcome` + `write` records from `tool_use_result.filePath`; `system.init.session_id` → `state.cliSessionId`; `system.compact_boundary` or `compact_result: "success"` marks CLI compaction; `result` → `usage` (input+cache tokens, `total_cost_usd`), then one `engine.context` (`engineSessionId`, `inputTokens`, `windowTokens`, `compacted`, `turnCount`) before `finished` (`error_max_turns` → `turn_limit`). Cancel → `interrupt` control_request then kill tree after 3 s. Each `tool_result` feeds a `LoopGuard`; a trip sends `interrupt`, kills the CLI and finishes `loop_guard` (the session's loop-guard divert then applies, as above). Exit without `result` → stderr tail via `classify` (auth → "Claude CLI not logged in"). Stale `--resume` clears the id and retries once with the same unseen-message recap. Verbatim stream-json captures in `modules/engines/test/fixtures/`.

**Process spawning** (Windows `0xC0000142` mitigation): children that never need input get no inherited stdin — the interactive `claude-code` run keeps a pipe (stream-json input + control traffic), the `SidecarSupervisor` keeps a pipe (stdin *is* the NDJSON RPC link) — everything else is `stdin: "devnull"`: `nodeSpawn` maps it to `stdio: ["ignore","pipe","pipe"]` with `stdin`/`write`/`end` as no-ops (used by `loginStatus` and `claudeComplete`), the VS Code `procRun` spawns `ignore` stdin + `windowsHide`, the JetBrains `ProcessRegistry` redirects input from `NUL`/`/dev/null` (its waiter thread always emits `proc.exit` — catch-all → code -1 — so `proc.done` can never pend forever), and the evals `nodeHost`/`sh` helpers do the same; the per-turn MCP server is in-process HTTP, not a spawn. `ProcessHandle` is `cancel`/`killTree`/`done` only — there is no stdin write path on host processes (the `claude-code` `SpawnedProc.write` is a different type and stays). `kernel/procStart.ts` owns `isStartFailure` (3221225794 / -1073741502 only), `exitCause` (a lookup table: -1 killed-or-never-started, 126 `not executable`, 127 `command not found`, 129–192 → `killed by signal <n>` naming 2/9/15, Windows `0xC0000142`/`0xC0000005`/`0xC000013A`/`0xC0000135` — the signed Java form is normalised first — and `undefined` otherwise) and `withStartRetry` (wraps `proc.run`: a bare start failure — no output, not cancelled — retries once after 250 ms; the VS Code and sidecar-remote `proc.run` are wrapped, each sidecar attempt getting a fresh handle id). Spawn-level failures surface a cause instead of a bare code: `SpawnedResult.spawnError` carries the child `"error"` event message (code -1) for CLI spawns, host runners resolve `done` `{code: -1, cause}` (VS Code `procRun` and the evals `nodeHost` set `cannot start <argv[0]>: <message>` — also emitted on `onData` — or `killed by signal <signal>` when the child exits with no code; the sidecar `remoteProcess` sets `cannot start …` when the run request fails; `withShellEnv` sets `cancelled before start`), `loginStatus` retries once on a start failure (`auth status: <exitCause>`), `claudeComplete` retries once (`Claude CLI <exitCause>`), and `claude-code` retries a lineless start failure inside the existing 2-attempt loop without dropping `engineSessionId` (`Claude CLI <exitCause>` on the last attempt). `RunTerminal`, check `command_failed` evidence and the change-tracker `must()` append ` (<cause>)` after the exit code when defined, where the cause is `done.cause ?? exitCause(code)`. **Shell env** (`kernel/shellEnv.ts`): `resolveShellEnv(run)` resolves the user's login-shell environment once per `run` function (cached by `WeakMap`) by spawning `[$SHELL ?? "/bin/sh", "-ilc", "printf '%s' __STEWART_ENV__; env -0"]` and parsing only the `env -0` output after the last `__STEWART_ENV__` marker (interactive rc noise before it is ignored; `PWD`/`OLDPWD`/`SHLVL`/`_` dropped); 5 s timeout (`killTree` then `{}`), non-zero exit → `{}`, missing marker → `{}`, spawn throw → `{}`, Windows → `{}` with no spawn, never rejects; only success and the win32 `{}` stay cached — a failure deletes the cache entry so the next call retries the shell. `withShellEnv(run)` wraps `proc.run` (handle stays synchronous, same deferred-start shape as `withStartRetry`; cancel/killTree before the inner starts prevent the spawn and resolve `done` `{code:-1, cause:"cancelled before start"}`) so every spawn runs under `{...shellEnv, ...opts.env}` — caller env wins; empty shell env + no `opts.env` passes opts unchanged. Both host seams wrap it outside `withStartRetry` (`hosts/vscode/src/procRun.ts`, `packages/sidecar/src/host.ts`), so check commands run with the login-shell `PATH` (nvm node) rather than the IDE's; a check command emits `command_unavailable` evidence (`check could not run (environment): <command_failed detail>`) only when the producer-reported cause starts with `cannot start` or the exit code is 126/127 — a fault, not a task failure — treated like `command_failed` everywhere else (e.g. `runOutcome`); matching output text like `Cannot find module` no longer counts.

### 3c. Qualification (`@stewart/setup` `conformance.ts` + `conformanceClaude.ts`, `CONFORMANCE_VERSION = 2`)

Two suites write `Qual {passed, at, version, detail?, context?}` records into `channels.yaml` `modelCaps.<model>.qualified` (same write path as bench `perf`). **Agent suite**: refused without running when `tools === "none"` or a known context < 32000. For `claude-cli` channels the agent suite is a real `claude-code` engine turn in a per-run scratch dir (`<stateDir>/qualify/<uuid>`): `notes/todo.txt` is seeded, the same prompt runs with an empty `ToolRegistry`, `maxTurns` 8, 180 s, and an approve that allows file previews inside the dir, `wc ` commands and read-only calls (everything else is rejected with a hint); wc success is tracked from `tool.request`/`tool.outcome` events; scratch files are deleted afterwards. Other channels run one `nativeLoop` turn against an in-memory sandbox (`notes/todo.txt` = "alpha\nbeta\n"; ReadFile/EditFile/WriteFile/RunTerminal; fake proc where only `wc -l` works, printing `3 notes/todo.txt`; auto-approve; maxTurns 8; 120 s): pass iff the file is exactly `alpha\nbeta\ngamma\n`, a `wc` RunTerminal call succeeded, and the reply contains `3`; detail names the first failed criterion. After either agent suite passes, the record's `context` is the model's known window; when unknown, a **window probe** runs first — one no-tools request whose ≈84,000-char message (≈28k real tokens: numbered filler lines) asks for the code word on its first line, sent over `channel.chat` for text channels or one `claude-code` engine turn for `claude-cli` — pass iff no error, not truncated, the word is echoed, and reported input usage (when present) is ≥ 20k; the pass records `context: 32000` (a verified 32k-class window), failure refuses "context window below 32000". **Function suite**: one plain request; the reply (optionally one ```json fence) must parse to `{"sum": 42, "word": "trawets"}`. Triggers: the wizard probe qualifies each green candidate inline (results land on `SetupProbeItem.qualified`, stage in `core.qualRecords` and persist on `setup.approve`; `setup.recommend` sees the staged records via `withSessionQualified`, a read-only config overlay where the session record wins and `undefined` keys are skipped), and `setup.qualify {channel, model}` (Settings "Qualify" button) runs and persists immediately. `scoreAssignments` refuses candidates without a passing record for the role's `kind` (missing counts as not qualified) or failing its `needs` (vision, `minContext` default 32000 for agents); wizard Apply (`buildAgentsForRoles`) writes an agent for every role-bound pair and every green candidate that passed at least one qualification suite (`passedPairs`), and proposes `chain` (qualified candidates, free/local then cheapest, claude-cli last, max 3) on each assignment. The AI-refine path applies the same role `kind`/`needs` (`hardRefusal` with role meta) and refuses never-probed models. `roles.assignAgent` refuses an agent the lead refuses; Settings role pickers list only qualified agents (plus vision when needed); saved roles are validated (`chainErrors`) so any refused bound/chain agent is a config error. Probe tool modes are `native` / `none` / `unknown` (v2 `shim` loads as `unknown`).

### 3e. Model refresh (`models.refresh`, `docs/archived_v3/MODEL_REFRESH_PLAN_2026-11-20.md`)

Settings "Refresh models" → host route → `models.refresh` (`packages/core/src/handlers/models.ts`, one per project via `refreshInFlight`). For each enabled channel `listModels()` runs in parallel with failures captured as `unreachable` (never diffed as empty); `extraModels` are unioned into the listed set. `@stewart/setup` `modelSync.ts` (`diffModels`, pure) diffs listed models vs `config.agents` → `added`/`gone` (with bound roles). Withdrawn = keep. A rejected handler still rejects its own caller but cannot poison the queue. Both lanes share the same `route` table and catch, which translates a thrown `models.refresh` failure into a typed `models.refresh.result {ok:false,error}` — the reply that clears the webview `refreshBusy` flag — while every other route keeps the generic `{type:'error'}` reply.

### 3f. Long builds (plans, milestones, checkpoints)

Lead-only tool `plan_write({goal, milestones:[{title, detail?, check:{command?: string[], files?: string[]}}]})` (`modules/session/src/plan.ts`, `PlanRunner`) validates every milestone has a `check.command` argv or `check.files`, then asks once via `ask_user` "Approve this plan?" with the plan rendered as user-facing Markdown (`renderPlanSummary`, shown formatted by the question card) — approval of the plan approves its check commands. Approve → baseline `tracker.begin("start")` (id persisted at `<stateDir>/sessions/<id>.plan`), the plan saved `active` at `.stewart/plans/<sessionId>.md` (`@stewart/tasks` `renderPlan`/`parsePlan`, argv rendered as a JSON array — a legacy backticked string parses as `["sh","-c",<str>]`), `plan.approved`. The session then **drives** the plan (`SessionService.drive`): after the lead task that approved it finishes `done`, each pending milestone runs as its own lead `runTask` of the same run — a `Milestone <id> of <n>` user message is appended (`milestone.started`), `plan_write` is not offered, `set_check` is reset, the contract is the milestone check (approved) + project verify + that task's `set_check`, `mustChange` applies to files-only milestones, and the baseline is the last done milestone's checkpoint (plan baseline for the first). Done → `tracker.begin("<id>")` is the milestone checkpoint + `milestone.done`; all done → plan `done`. Failed after the chain (and the interactive retry) → milestone `failed`, plan `paused`, `milestone.failed`, run fails `milestone <id> failed: <text>`; cancel/cost-cap → plan `paused`, milestone stays pending. A non-done lead task pauses an active plan; a normal turn on a paused plan does not drive it. Transcript and plan file persist after every milestone; one `run.started`/`run.finished` per run, outcome `changed` = diff of the run's first baseline. An unfinished plan rides in the lead system prompt (`# Plan (<status>)`, ≤4000 chars). `chat.resume` starts a driver-only run (`Resume plan: <goal>` — a failed current milestone resets to pending); `chat.revert` restores `"turn"`, a named/latest/"baseline" checkpoint via `tracker.restore`, resets milestones after it to pending and pauses the plan, and emits `run.reverted`. `history.load` returns a `plan` summary; the webview shows a plan card with per-milestone Revert buttons and a Resume-plan action.

### 3g. Delegation

`delegate({role, task, report?, check?, scope?, schema?})` (lead only, `parallel: true`, `noTimeout`; the lead prompt limits it to read-only parallel work, reading that would flood the lead's context, and narrow checkable work for a cheaper qualified role; `check = {files?, command?}` is verified by code after the child stops, the command goes through the approval gate — refusal is `command_denied` check evidence) runs a child turn through the same `runTask` path (contract = `delegate` check + `.stewart/project.yaml` `verify:` for write-capable roles; `interactive: false`): agent = first eligible of `[role.agent, role.secondary]` else the lead's resolved agents (`task.started`'s `agentId` and the admission slot use the same first-eligible pick); engine via `engineFor` (same engine id, incl. `claude-code`); tools = `projectTools(...).for(role)` + `load_skill` (children never get `delegate`/`health_report` — depth 1); system = role prompt + skill index + project notes; transcript = the task as one user message (`report: "health"` prefixes the authoritative report contract and declared `scope`; a read-only health delegate must pass structured `scope` entries and failed health children return check evidence plus a `health_report` instruction, never rejected worker JSON; no `load_skill` dependency); `maxTurns` = `role.turnBudget` (not `runTurnLimit`; ≥ 1000 is unbounded here too); up to 4 children run concurrently, but children whose role has write tools (and are not `kind: function`) run behind a FIFO read/write lock: a waiting writer blocks later readers and holds while readers finish; readers share (function tasks take no lock). A `kind: function` role takes `schema` (JSON Schema object) and runs `engine.complete` per qualified `function` agent in chain order (no tools, no transcript — native channels carry `responseSchema`, OpenAI `response_format: {type: "json_schema"}` / Ollama `format`, retried once without it on a 4xx rejection; `claude-cli` agents run one `claude -p --json-schema` turn; a reply that is not a schema-valid JSON object escalates to the next agent); the delegate result is `status: done` + the JSON. Read-only roles (no write tools) get the generic read-only terminal guard; every child's approve is `policyApprove(role, gate)` — the same `decide` before-the-fact rule for native tools and `claude-code` `can_use_tool` previews (file edits need a project path not in `.git/`/`.stewart/` (`.stewart/scratch/` allowed) and matching `writePaths`, commands need `RunTerminal` and the read-only allow-list for read-only roles — which ignores `2>&1`/`>/dev/null`-style redirects, drops safe segments not fed by a pipe (`<program> --version` and `-v` only for node/npm/pnpm/yarn/npx/git/tsc/docker, `cd <dir>`, print-only `sed -n 'N(,M)p'`; `true`/`false` are allow-listed programs), refuses `sort -o`/`tree -o`/`date -s`/`find -delete|-exec|-ok|-fls|-fprint*`/`git --output[=]`/`rg --pre*|--hostname-bin`/second-`uniq`-positional writes, skips `git -C <dir>`/`--no-pager` before the subcommand, allows `git branch` only with list flags, and refuses test runners with a "delegate to tester" hint). Under `claude-code` before-the-fact enforcement depends on the CLI sending `can_use_tool`; a restricted-role **policy backstop** catches what slips past after the fact: at verify time every path in the tracker diff must pass `decide(role, {kind:'write'})`, each failure emits `policy_violation` evidence (`changed outside role policy: <path> (<reason>)`, capped at 10 paths + "and N more") and the task fails — no auto-revert. Unrestricted roles (the default lead) are not backstopped, and `.git/`/`.stewart/` changes are outside the tracker's view by design. Each child takes its own `tracker.begin("task-<taskId>")` baseline at start and diffs it at check time (the shared tracker serializes calls); a parallel read-only child's diff can only contain the lead's own output, which is nothing while the lead is blocked in `delegate` — no special handling. Write records feed the lead's plan and the `write_failed` rule only. Each child's check is its `delegate` `check` ({files?, command?}) plus `cites: true` and `needsRead: true` for read-only roles (every cited path:line must exist, and the child must have made at least one successful read) and, for `report: "health"`, `schema: "health"` + `healthScope` (exactly one ```json block validating as `HealthReport`, all report paths must exist, every declared file/range appears in `files` — a null/empty `files[].range` counts as a whole-file entry — unverified findings outside scope fail; a scope-less health task is a checks task and may report only `checks[]` — non-empty `files`/`findings`/`notChecked` are rejected). Status is `done` iff engine stop + check passed; the delegate result text is `status: <s>` + the reply (8k cap) + `check: <evidence>` on failure — a failed child is a tool success, not an error. Events: `task.created`/`task.started`/`task.done`/`task.failed` with `taskId`+`roleId`; one bounded format-only health repair emits `task.repair` before normal escalation (no tools, max one turn, only when every failed evidence is repairable `health_invalid`); child text/tool rows carry `taskId`; usage meters to the ledger under the child role and counts toward the run cost cap. Child transcripts save to `<stateDir>/sessions/<sessionId>/<taskId>.json` (not in the history list). `health_report()` merges successful `report:"health"` children via `@stewart/code-health` (`mergeReports` + `aggregate` + `renderReport("issues", ...)` + `scanMetrics`/`summarizeMetrics`), writes `.stewart/reports/health-<runId>.md` through the host, returns the rendered text + path; fails "no health reports in this run" only when no health child ran; it tracks declared/checked/missing scope and failed task reasons (a failed task stays listed but does not make coverage partial once its scope is re-checked by another task; a failed scope-less checks task does), adds missing scope to `notChecked`, renders `Coverage: complete|partial|unknown`, and appends a "still running — call again" note when delegated health tasks are in flight so an early snapshot cannot pass for the final report. A `done` lead result is downgraded to `run.finished` `failed` with the coverage verdict when health tasks left scope unchecked or a checks task failed. Shipped roles: `lead`, `explorer` (read-only search), `reviewer` (read-only review), `planner` (read-only; returns milestones with checks), `tester` (writes only test paths, runs them); `project-health` skill on the lead orchestrates batched reviewer runs.

### 3h. Business policy (`docs/archived_v3/BUSINESS_POLICY_PLAN_2026-11-20.md`)

Outbound content rules (`@stewart/business-policy`: `passwords`, `privacy`) are a content gate beside the action gate (`decide`/`policyApprove`). Effective rules per channel = `channels.yaml` `security.<rule>` override, else `settings.yaml` `security.<rule>` (default on; tri-state in the UI: inherit/on/off); `ChannelService.rebuild(channels, host, security)` resolves them (`rulesFor`) and calls `ManagedChannel.setRules`, so reloads re-apply and limiter state still survives. Seams: `ManagedChannel.chat` (native loop, function runs, compaction: every request) via `screen()`; the claude-code engine screens the system prompt, the unseen-message recap and the user line in `claudePolicy.ts` before spawn (older, already-sent messages are ignored); `claudeComplete` screens system + input. A hit in system/user/assistant content throws `BusinessPolicyError` (nothing sent; engines emit `policy.notice` `blocked`, redact the offending user/assistant messages in the persisted transcript so the session stays usable, and finish `error` with `business_policy: blocked outgoing message to <channel>: <rule> in <where> #<n> (<hint>)`); a hit in a tool result replaces it with `[output withheld by business policy: <rule>]` in the outgoing copy only (`withheld` notice once per message; the run continues; tool results are withheld on the transcript *before* `forNative` renders another engine's tool calls into assistant text, and compaction summarises through the same rules — tool results withheld, matching messages blanked, archive keeps originals). `passwords` reads `key: word` with an unquoted plain-letter value as prose, so only `key=value`, quoted, or non-letter values count. The task chain does not escalate to another agent on the same channel after a `business_policy:` failure (`runChain`), a different channel proceeds. Claude CLI channels with a rule ticked: `cliPolicyGate` (session `policyGate.ts`) asks Continue/Stop once per lead session + channel (memory only; children inherit the answer, else fail `business_policy: refused …` with a `refused` notice) because the CLI reads files itself. `policy.notice {runId, channel, rule, action: blocked|withheld|refused, where, msgIndex}` (protocol) never carries matched text; the webview renders an activity row. UI: Settings → settings → Security (global checkboxes + "Apply to all channels", which clears every channel override after a confirm) and a Security block per channel (`channelSecurity.tsx`, Inherit/On/Off, `inherited`/`custom` marker, Reset to default, claude-cli hint). Limits: images are not inspected; custom patterns are not built; the Claude CLI's own file reads are unseeable.

### 3i. Removal cascade

`config.set` on user-layer `channels.yaml`/`agents.yaml` runs `cascadeConfigSet` (`packages/core/src/handlers/configCascade.ts`) after the file write; `core.reload` happens in `finally` so a cascade write failure still reloads. Pure logic lives in `@stewart/setup` `cascade.ts`: `detectIdChange` diffs the *raw user rows* (pre-write `ctx.userLayer` vs the incoming document — defaults are never materialized into user files; `[]` when the file is absent or unparseable, so the cascade never rewrites a broken file) — a rename is one id gone at an unchanged list length where the item at that index now carries a new id or one duplicated in the incoming list (a merge onto an existing id), everything else gone is a removal. `cascadeRemoval` drops agents on a removed channel plus explicitly removed agents, then resets bound roles: a removed `secondary` (field or legacy `chain` tail) is dropped; a removed effective `agent` promotes the surviving `secondary` (or chain tail), else the role unbinds and inherits the lead's chain — shared `applyDecisions`/`unbindRole` in `modelSync.ts`, so `models.refresh` and the wizard get the same rule. Legacy `chain` rows are kept consistent so `migrateRoleChain` cannot resurrect a dead binding. `repointRename` re-points `channel`/`agent`/`secondary`/`chain` references instead of removing them. Trusted project `roles.yaml` rows get the same transform via `projectGuard`/`projectStore` (outranks the user file field-by-field); untrusted or project-layer saves never cascade. The wizard's `setup.session.removeChannel` cascades through the staged `agents.yaml`/`roles.yaml` drafts the same way. In the webview, Remove becomes a two-step inline confirm (`ItemCardTitle`): channels always confirm naming the affected agents/roles, agents only when a role binds them (`removalImpact.ts`).

### 3j. Harness efficiency (`docs/HARNESS_EFFICIENCY_PLAN.md`; measure with `scripts/analyze-debug-log.mjs`, see EVALS.md)

- **E2 reasoning control (openai-compatible).** `channels.yaml` `reasoning: none|reasoning_effort|enable_thinking` (default `none` = nothing sent). `openaiReasoning.ts` `reasoningBody`: `reasoning_effort` field → `think:false` = `"none"`, `effort` low/medium/high passed, `max` → `high`; `enable_thinking` → `chat_template_kwargs.enable_thinking` false for `think:false`, true for `think:true` or effort high/max, else nothing. `think:false` beats effort. `probeCaps` (setup probe; only when a field is configured) sends a trivial prompt without, then with, the off field and compares `reasoning_tokens`; stores `modelCaps.<model>.reasoningControl` (`true` cut them, `false` did not/rejected → field never sent; absent = not probed or model does not reason → field still sent). `ManagedChannel.reasoningRouting(model)` = field configured, caps not `false`, and the provider has not rejected the field. Probe results live in the in-memory probe cache (not persisted), so after a restart a model is unprobed and the field is still sent; as a backstop `ManagedChannel.stream` retries a 400/422 on a request that carried the field once without `think`/`effort`, remembers the rejection per model until the config reloads (`update()`), and never sends the field again. The Settings channel editor has a `reasoning field` drop-down.
- **Routine-turn policy** (`engines/reasoningPolicy.ts`, native loop only, only when `reasoningRouting` and `turn.think` is unset — an explicit `role.think` stays authoritative): full effort on the first turn, after any failed or non-routine call, after a loop-guard warning and on the report-only last turn; `think:false` after a batch whose calls all succeeded and are in `ReadFile/Search/FindFiles/ListCodeFiles/ReadImage/GetDiff`.
- **Reasoning overrun guard**: in the same condition, a request that streams > 20,000 reasoning chars with no content or tool call is aborted (own `AbortController` chained to the turn signal) and retried once with `think:false`; once per run. Emits `EngineEvent {kind:"diag", tag:"reasoning_overrun"}`, which `taskEvents.onEvent` writes to the host log (`reasoning_overrun: <n> reasoning chars…`), no bus event.

- **E4 window-aware tool output caps** (`engines/outputCap.ts`): one tool result is capped at `min(20,000, window × 4 × 0.08)` chars (≈10.2k at 32k; unknown window assumes 32,768). `EngineTurn.window` (tokens) is set by `taskRun` from `agentContext`. Over the cap, `ReadFile`/`Read` keep a head window ending on a whole line plus `[truncated at line L of T: N chars omitted; use start_line/end_line to read ranges (next: start_line=L+1)]`; other tools keep 70% head + 30% tail around `[output truncated: N chars omitted]`.
- **E5 re-read guard** (`engines/readGuard.ts`, native loop): per run, `ReadFile` path + line range → content hash, call id and model turn. The read always executes (so the hash reflects the file on disk, including writes by any tool); if the hash equals the earlier read's and that earlier tool message is still in the transcript in full (not compacted away or trimmed to a stub), the model gets `[Stewart] already read at turn N; unchanged. <lines>, starts: <first line>. Use that earlier result, or read a different range…` instead of the content. A changed file, another range or path, or a compacted/trimmed earlier result re-reads in full. The loop guard still sees the note as the (repeated) result.
- **E6 exploration discipline**: the lead system prompt (`session/lead.ts` `EXPLORATION_RULES`, appended to every lead prompt so existing `roles.yaml` files get it) says to use `Search`/`FindFiles` rather than shell sweeps and to batch independent reads. `engines/exploreGuard.ts` (native loop; nudges only, never trips): ≥ 5 `RunTerminal` calls on the same absolute directory prefix (first 4 segments of `cwd`, else the parent of the first absolute path argument; paths inside the project root and relative paths are ignored) within 20 model turns → one `[Stewart]` user message per prefix asking to summarise, act, or ask the user; and a role that has `WriteFile`/`EditFile`/`ApplyPatch` that goes 40 model turns without a successful write gets a `[Stewart]` message to give a one-line progress note and re-plan (repeats every 40 turns; read-only roles never). Both emit `diag` `exploration_nudge` to the host log and make the next request a full-effort one (E2).
- **E7 long-run agent selection**: `loadEffectiveConfig` appends to `errors` (shown in Settings) a `warning: role <id>: agent '<a>' has a <n>-token window but the turn budget is <b>…` for each enabled agent-kind role whose bound agent has a known window ≤ 32,768 while its budget is > 40 (the lead's budget is `settings.runTurnLimit`; unlimited counts; unknown windows are not warned) — `roles-skills/roleWindow.ts`. Role field `heavyAgent` (agent id; validated: unknown or refused → error): plan milestone tasks (`TaskSpec.baseline` set) of that role start on it when eligible, the normal chain after (`session/heavyAgent.ts` `heavyFirst`, applied in `runTask`; other tasks and the loop-guard divert are unchanged). **Not built**: re-probing the context window on `models.refresh` (a larger probe is a 60k+-token request per model, so it stays an explicit Qualify action) and showing the probed value in the agent row.
- **E3 compaction that fits the window**: measured-token trigger, trim-before-summarise, second trim pass, 4-request cooldown, `Files read` digest — rules in §6 "Compaction".

## 5. Config and state

- Files: shared `~/.config/stewart/{channels,agents,roles,settings}.yaml`, `skills/` — one dir for every IDE and project (`@stewart/config` `userDir.ts`; Kotlin mirror `UserConfigDir.kt`). Created on host start. Files must be `.yaml`; project `.stewart/{roles.yaml,project.yaml,skills/}` (trusted workspaces only; `project.yaml` `verify:` = list of argv arrays run as contract commands on every write-capable task; `readRoots:` = absolute directories exposed to read/list/search/image tools after realpath checks, never writes or terminal cwd). Old keys (budgets, recovery, lease/plan settings, `fallbackAgent`) parse and are ignored. ## 6. Known gaps

- Change tracking runs in the workspace-root repo only: writes inside nested git repositories never appear in the tracker diff — the outcome's `changed` merges successful tool-write paths, but shell-made changes in nested repos stay invisible.

- `EngineTurn.hostTools` carries the session tools (`delegate`, `health_report`, `plan_write`, `load_skill`, `ask_user`, `set_check`): the native loop merges them into its registry; the `claude-code` engine serves them over a per-turn MCP streamable-HTTP server on 127.0.0.1 (random port + bearer token, `modules/engines/src/mcp.ts`; JSON-RPC `initialize`/`tools/list`/`tools/call`) with `--mcp-config` + `--allowedTools mcp__stewart__*`; tools with `requiresApproval` (e.g. `set_check`) go through `turn.approve` inside the MCP server before they run. Children get no `hostTools` (depth 1).
- Compaction (`session/compact.ts`, trimming in `compactTrim.ts`): before each lead turn and, before every model request when `engine.caps.ownContext` is false (`beforeModelTurn`), when the prompt is past 60% of the agent's window (32k when unknown). Size = the provider's `usage.in` of the previous request (the native loop passes `{tokens, len}` = prompt tokens + transcript length that request covered) plus the 4 chars/token estimate of messages appended since; the plain estimate before the first response or after a compaction. Order: (1) **trim** — tool results older than the last 4 messages shortened in place to a 1,500-char head(2/3)+tail(1/3) stub with a `[Stewart: tool result truncated…]` marker (originals appended to the archive first; idempotent; no model call); (2) if still over and not within 4 requests of the last model summary (`CompactState.sinceSummary`, kept per turn on `TurnWork`; overridden past 90% of the window), one range is summarised by one plain request to that agent and replaced by a `[Summary of earlier conversation] #<chunk>` user message — everything before the last two user turns, or inside one long turn the work between the open task and the last ≤8 messages (cut at an assistant message), only when that range is at least half the (trimmed) estimate; the summariser is asked for a `Files read` digest (path, purpose, key symbols) and sees up to 1,500 chars of each `ReadFile` result labelled with its path; (3) if the transcript is still over the threshold after a summary, a harder trim (keep last 2 messages, 800-char stubs) instead of another model call. The removed messages are appended to `<stateDir>/sessions/<id>.archive.jsonl` as `{chunk, message}` first; `history.load` (`fullHistory`) expands summaries back (trimmed results are archived as `trimmed` lines and `expandArchived` puts each original back, matched by tool-call id and the stub's kept head, so history shows the full text). A failed or empty summary leaves the step-1 transcript. `beforeModelTurn` resolves true when the transcript changed, which clears the loop's measurement. The active plan rides in the system prompt; the open task stays verbatim. Skipped when the engine owns context (claude-code).
- ACP (§7 of the design): not built; see `docs/archived_v3/NEW_DESIGN_2026-11-13.md` §8.1 #11.
- Claude CLI `chat()` is intentionally unsupported (claude-code engine owns that transport); listModels/loginStatus/probeCaps remain for setup. The wizard probe smokes claude-cli candidates through `smokeClaude` (one `claude-code` engine turn, all calls denied; agent id `smoke:<channel>:<model>`) via the runner's `deps.smoke` seam — never `channel.chat`.
