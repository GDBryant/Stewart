# Stewart — Architecture Now

Living description of the code **as it is**. Update in the same commit as any change to modules, run paths, protocol, config, or host wiring. Plans live elsewhere (`docs/building/` = active; `docs/archived_v2/` = superseded v2-era docs).

Last updated: 2026-11-13 (§8 audit fixes; history: `git log -- docs/ai_docs/ARCHITECTURE_NOW.md`).

## 1. Layout

```
packages/
  protocol/    JSON-RPC types, PROTOCOL_VERSION, capability negotiation (src/index.ts)
  core/        all logic; no host imports
  sidecar/     Node stdio JSON-RPC server for JetBrains (rpc.ts, server.ts, host.ts reverse-RPC → HostPort, debugSink.ts)
  webview/     Preact chat + settings + setup wizard, one bundle for both hosts
  evals/       outcome eval suite: fixture repo, code-scored tasks, Node HostPort runner over a real Core (docs/ai_docs/EVALS.md)
modules/       17 `@stewart/<module>` packages, each with a `README.md` (purpose, surface, owns, deps). Modules import only strictly lower layers (`scripts/layers.json`, `pnpm check:layers`); every package is `composite` with a 90/80 coverage gate. Product version 3.0.0 (`hosts/vscode/package.json`, `build.gradle.kts`). Layers: see table in §1a.
hosts/
  vscode/      in-process core; host.ts implements HostPort via vscode API; routes.ts = webview message route table + dispatchAndReply
  jetbrains/   Kotlin: SidecarSupervisor (bundled Node, restart/backoff), HostRequestHandler, JCEF WebviewRouter
```

```
webview ─postMessage─ host ─(in-process | stdio NDJSON JSON-RPC)─ Core.dispatch
                                                                    │
                                                 ConfigStore    ChannelService   SessionService ─→ Engine
                                                 (YAML, schema) (adapters)       (lead turns)      ├ native-loop ─→ channel.chat
                                                                                                   └ claude-code ─→ Claude Code CLI
```

## 3. Run paths

There is exactly one chat path: the lead session.

### 3a. Lead path

`handleChatSend` (no `/direct`, no orchestrated path, no classifier) resolves the enabled `lead` role and calls `ProjectCtx.sessions.send`. `SessionService` (`@stewart/session`) loads the `ChatHistoryStore` transcript + `<stateDir>/sessions/<id>.engine.json`, appends the user message, resolves the lead's **eligible chain** — `eligibleChain` (roles-skills `chain.ts`): `role.chain` else `[role.agent]` else the lead's chain (for lead: the first agent); only agents `agentRefusal` accepts (passing `qualified[kind]` record; window ≥ `needs.minContext` when the window is known — an unknown window is admitted because many providers report none; vision when needed), in chain order; empty → failed "no qualified agent for role <id>: run Qualify in settings" — builds the system prompt (lead prompt + one-line skill index + `loadProjectContext` cut to 8000 chars) and tools (`projectTools(...).for(lead)` + `load_skill` + `ask_user` via `interaction.questionPrompt` + `delegate` + `health_report` + `set_check` + plan tools), then runs `engineFor(channel type)` — `claude-code` for `claude-cli` channels, `native-loop` for everything else. `maxTurns` = `lead.turnBudget` (`unlimited` → 200).

The session emits `run.started`, `text_delta`/`reasoning_delta`, `tool.request`/`tool.outcome` (roleId `lead`); approvals route through `permissions.gate` so `chat.approve`/`chat.answer` keep working; usage meters into `RunLedger` (role `lead`) with `cost.summary` when cost > 0 and abort + failed "cost cap reached" past `costLimit.perRunUsd`. Before the first write to a file the session snapshots its content (`tool.request` of a write tool; the path is made project-relative so absolute Claude CLI paths match the relative write records). At turn start it also records the git worktree state (`worktreeState`, ignoring `.stewart/`, `.claude/`, `node_modules/`; undefined outside git — so outside git, edits made only through shell commands count as no change). After the engine stops it runs `runCheck` on `declaredCheck(input, set_check)` — failed writes, files that must exist **and differ from their snapshot**, the command declared with `set_check({command, files?})` (approval-gated like any command, under both engines; must exit 0), empty reply — plus `edit: true` when the request is an imperative edit (`isEditGoal`; questions are not): some file must have changed by a write tool or on disk (git diff, so shell edits count), unless the declared command passed — plus `cites: true` when no file changed and the request reads as a review/report (`isReportGoal`) — emits `check.result`, and finishes `done` only when the engine stopped normally **and** the check passed. The last attempt's check result is reused by the final check when nothing was written or declared since, so a declared command runs once per turn (`cancelled` on cancel, else `failed` with the engine error or check evidence). Transcript + engine state persist after every turn, including failures. `chat.cancel` → `sessions.cancel`. Turns on one session serialize.

**Escalation over the chain.** Each attempt runs the next eligible agent. A failed attempt — check failure, engine error, `turn_limit`, `loop_guard` — escalates: a handover user message is appended (`Handover: the previous agent (<id>) did not finish this task. Goal: … Tried: … Failing evidence: … Continue from the current state of the files.`), `run.escalated {from,to,reason}` is emitted (reason `check_failed`|`error`|`turn_limit`|`loop_guard`), and writes/changed-file records accumulate so the final check covers all attempts. "Tried" outcomes are matched to calls by `callId`. No escalation on cancel or cost cap. After the last agent fails the session asks via `ask_user` ("All agents for this task failed. … retry once more on <lastAgentId>, or stop.", options `["Stop"]`): any other answer retries that agent once with the guidance appended; `Stop`/timeout fails with the evidence. Delegated children escalate along their own role chain identically but never ask the user — they return `status: failed` to the lead.

### 3b. Engines

`native-loop` (`engines/nativeLoop.ts`): per model turn `channel.chat` with native `tools` (no text shim), streams text/reasoning/usage, appends assistant/tool messages to the transcript, executes calls sequentially — consecutive calls on tools flagged `parallel: true` run concurrently via `Promise.all`, preserving tool-message order — (validate → preview → `approve` → 120 s timeout — skipped for `awaitsUser` tools (`ask_user`, `plan_write`) and `noTimeout` tools (`delegate`, `milestone_done`) — 20k-char 70/30 cap, image results pushed as user image messages), emits `write` records for WriteFile/EditFile/ApplyPatch, finishes `stop`/`turn_limit`/`cancelled`/`error`/`loop_guard`. `beforeModelTurn` (session: compaction) runs before every model request. The loop guard (`engines/loopGuard.ts`, also used by `claude-code`) trips when the same call (tool name + canonical JSON args) fails twice in one run, when the same call returns the same result three times, or after 6 consecutive model turns where every call failed or was invalid — the session treats it like `turn_limit` (escalates).

`claude-code` (`engines/claudeCode.ts`/`claudeLines.ts`) spawns the Claude Code CLI as a full agent in the project root: `claude -p --input-format stream-json --output-format stream-json --verbose --permission-prompt-tool stdio --include-partial-messages --model <normalizeModel(agent.model)>` plus `--append-system-prompt` (non-empty system only), `--max-turns`, and `--resume <state.cliSessionId>` when stored. It uses the CLI's own tools — `turn.tools` is ignored — under `claudeChildEnv` (host env minus `ANTHROPIC_API_KEY`/`ANTHROPIC_AUTH_TOKEN`, `MCP_TOOL_TIMEOUT` defaulted to 6 h because Stewart's MCP tools wait on approvals, plan approval and child runs, plus `cfg.extraEnv`). The last user message goes to stdin as one stream-json line (images as base64 blocks); stdin stays open for control traffic, closed after `result`. `can_use_tool` control requests route through `turn.approve` with a mapped preview (Edit/Write/MultiEdit/NotebookEdit → file preview relativised to cwd, Bash → command, others → `OTHER`); other control subtypes get an error response. Deltas dedupe by `api_message_id`; `tool_use`/`tool_result` → `tool.request`/`tool.outcome` + `write` records from `tool_use_result.filePath`; `system.init.session_id` → `state.cliSessionId`; `result` → `usage` (input+cache tokens, `total_cost_usd`) then `finished` (`error_max_turns` → `turn_limit`). Cancel → `interrupt` control_request then kill tree after 3 s. Each `tool_result` feeds a `LoopGuard`; a trip sends `interrupt`, kills the CLI and finishes `loop_guard`. Exit without `result` → stderr tail via `classify` (auth → "Claude CLI not logged in"). Stale `--resume` clears the id and retries once with a ≤6-message ≤4000-char recap. Verbatim stream-json captures in `modules/engines/test/fixtures/`.

### 3c. Qualification (`@stewart/setup` `conformance.ts`, `CONFORMANCE_VERSION = 1`)

Two suites write `Qual {passed, at, version, detail?}` records into `channels.yaml` `modelCaps.<model>.qualified` (same write path as bench `perf`). **Agent suite**: refused without running when `tools === "none"` or context < 32000; `claude-cli` channels pass by engine type without a run (deliberate exception: a real run needs the live CLI in a scratch directory; see design §8.4). Otherwise one `nativeLoop` turn against an in-memory sandbox (`notes/todo.txt` = "alpha\nbeta\n"; ReadFile/EditFile/WriteFile/RunTerminal; fake proc where only `wc -l` works, printing `3 notes/todo.txt`; auto-approve; maxTurns 8; 120 s): pass iff the file is exactly `alpha\nbeta\ngamma\n`, a `wc` RunTerminal call succeeded, and the reply contains `3`; detail names the first failed criterion. **Function suite**: one plain request; the reply (optionally one ```json fence) must parse to `{"sum": 42, "word": "trawets"}`. Triggers: the wizard probe qualifies each green candidate inline (results land on `SetupProbeItem.qualified` and persist on `setup.approve`), and `setup.qualify {channel, model}` (Settings "Qualify" button) runs and persists immediately. `scoreAssignments` refuses candidates without a passing record for the role's `kind` (missing counts as not qualified) or failing its `needs` (vision, `minContext` default 32000 for agents), and proposes `chain` (qualified candidates, free/local then cheapest, claude-cli last, max 3) on each assignment. The AI-refine path applies the same role `kind`/`needs` (`hardRefusal` with role meta) and refuses never-probed models. `roles.assignAgent` refuses an agent the lead refuses; Settings role pickers list only qualified agents (plus vision when needed); saved roles are validated (`chainErrors`) so any refused bound/chain agent is a config error. Probe tool modes are `native` / `none` / `unknown` (v2 `shim` loads as `unknown`).

### 3d. Setup bench probe

`channel.probe --bench` (`packages/core/src/probeLoop.ts`) runs `nativeLoop` with one synthetic tool and an auto-approve gate; it aborts the turn the moment the probed tool's outcome arrives, so `toolReliability`/`editOk` measure "did the model issue a valid native call" in one round trip; `jsonOk` comes from a plain chat probe. Unknown measurements warn instead of hard-failing recommendations.

### 3e. Long builds (plans, milestones, checkpoints)

Lead-only tools `plan_write({goal, milestones[]})` and `milestone_done({id})` (`modules/session/src/plan.ts`, `PlanRunner`). `plan_write` is refused once the turn has already written files (plan before editing), validates every milestone has a `check.command` or `check.files`, writes `.stewart/plan.md` (`@stewart/tasks` `renderPlan`/`parsePlan` — exact round-trip format, written through the host; `.stewart` stays denied to model tools), then asks once via `ask_user` "Approve this plan?" (options Approve/Revise). Approve → baseline checkpoint `start`, `plan.approved` + `milestone.started` for M1; other answers leave no active plan. `milestone_done` only accepts the current milestone (first not done — a failed one stays current and blocks the rest); runs `runCheck` over the milestone check plus writes (lead and children) since the last checkpoint — a files-only check with no write since the last checkpoint fails; pass → worktree checkpoint, `milestone.done`, next `milestone.started` (all done → plan `done`); fail → `attempts+1`, tool-success `check failed...`, third failure marks `milestone.failed` and asks the lead to consult the user. An active plan is appended to the lead system prompt (`# Active plan`, ≤4000 chars). After a turn that wrote files or used plan tools (not on cancel/cost cap), the end-of-turn sweep checks only the current milestone (auto-pass + checkpoint when it passes); any milestone still not done fails the run `plan incomplete: <id> <title>: <evidence | not started | milestone failed…>`; the plan is `done` only when every milestone is. Checkpoints (`@stewart/tasks` `checkpoint.ts`, host proc/files only): git repos commit the whole worktree through a temp index under stateDir into `refs/stewart/<sessionId>` — HEAD, branches and the user's index untouched; non-git projects write `snap-<n>` manifests under `<stateDir>/checkpoints/` holding every file the session touched; before the first write to a file no manifest has seen, `recordOriginal` adds its pre-write content (null = absent) to every existing manifest, so reverting restores it or deletes files created later (state on disk, survives resume). `chat.revert` restores a named/latest/"baseline" checkpoint (worktree only; `.git`/`.stewart` preserved — git revert never restores `.stewart/`, ignored files untouched), sets milestones after the restored checkpoint back to pending (baseline: all) and emits `run.reverted`; `chat.resume` starts a lead turn "Resume the plan in .stewart/plan.md: continue at <id>: <title>" when the session plan is active. `history.load` returns a `plan` summary; the webview shows a plan card with per-milestone Revert buttons and a Resume-plan action.

### 3f. Delegation

`delegate({role, task, report?, check?, schema?})` (lead only, `parallel: true`, `noTimeout`; the lead prompt limits it to read-only parallel work, reading that would flood the lead's context, and narrow checkable work for a cheaper qualified role; `check = {files?, command?}` is verified by code after the child stops, the command through the approval gate) runs a child turn: agent = `role.agent` else the lead's resolved agent; engine via `engineFor` (same engine id, incl. `claude-code`); tools = `projectTools(...).for(role)` + `load_skill` (children never get `delegate`/`health_report` — depth 1); system = role prompt + skill index + project notes; transcript = the task as one user message; `maxTurns` = `role.turnBudget`; up to 4 children run concurrently, but children whose role has write tools (and are not `kind: function`) run one at a time (writer queue). A `kind: function` role takes `schema` (JSON Schema object) and runs `runFunction` per qualified `function` agent in chain order (no tools, no transcript; a reply that is not a schema-valid JSON object escalates to the next agent); the delegate result is `status: done` + the JSON. Read-only roles (no write tools) get the generic read-only terminal guard; for `claude-code` children (whose CLI keeps its own tools) `childApprove` applies the role profile before the gate (`childPolicy.ts`): file edits need a write tool and a path inside `writePaths`, commands need `RunTerminal`, read-only roles get read-only commands only. Children snapshot files before writing and feed the lead's plan (writes, copy-on-write originals). Each child gets the `tasks` `turnCheck` (with its own pre-write snapshots) plus `cites: true` for read-only roles (citations must exist; "no findings" needs a successful read) and, for `report: "health"`, `schema: "health"` (exactly one ```json block validating as `HealthReport`, all report paths must exist). Status is `done` iff engine stop + check passed; the delegate result text is `status: <s>` + the reply (8k cap) + `check: <evidence>` on failure — a failed child is a tool success, not an error. Events: `task.created`/`task.started`/`task.done`/`task.failed` with `taskId`+`roleId`; child text/tool rows carry `taskId`; usage meters to the ledger under the child role and counts toward the run cost cap. Child transcripts save to `<stateDir>/sessions/<sessionId>/<taskId>.json` (not in the history list). `health_report()` merges successful `report:"health"` children via `@stewart/code-health` (`mergeReports` + `aggregate` + `renderReport("issues", ...)` + `scanMetrics`/`summarizeMetrics`), writes `.stewart/reports/health-<runId>.md` through the host, returns the rendered text + path; fails "no health reports in this run" when empty. Shipped roles: `lead`, `explorer` (read-only search), `reviewer` (read-only review), `planner` (read-only; returns milestones with checks), `tester` (writes only test paths, runs them); `project-health` skill on the lead orchestrates batched reviewer runs.

## 4. Model facts

Per `channel/model`, facts come from: `modelCaps` in `channels.yaml` (user, wins — includes `qualified` records) ← probe cache (in-memory) ← bench `perf` ← catalog / live `priceList`; agent `price` wins for cost. `models/profile.ts` is the single merge; raw `modelCaps` reads go through `userCaps`/`capsFor` (`check:boundaries` forbids raw reads outside the allowlist).

## 5. Config and state

- Files: shared `~/.config/stewart/{channels,agents,roles,settings}.yaml`, `skills/` — one dir for every IDE and project (`@stewart/config` `userDir.ts`; Kotlin mirror `UserConfigDir.kt`). Created on host start. Files must be `.yaml`; project `.stewart/{roles.yaml,skills/}` (trusted workspaces only). Old keys (budgets, recovery, lease/plan settings, `fallbackAgent`) parse and are ignored. Role fields: `kind` (`agent` | `function`, default agent), `needs` (`vision`, `minContext` — agent default 32000), `chain` (agent ids, cheapest first); `agent` alone still works.
- Child transcripts live at `<stateDir>/sessions/<sessionId>/<taskId>.json`; health reports at `.stewart/reports/health-<runId>.md`; plans at `.stewart/plan.md`; snapshot checkpoints and the temp git index under `<stateDir>/checkpoints/`; checkpoint commits under `refs/stewart/<sessionId>`; plan baseline id at `<stateDir>/sessions/<sessionId>.plan`.
- State dir (HostPort): `ledger.jsonl`, `sessions/<id>.engine.json`, chat history (`ChatHistoryStore`, owned by `@stewart/session`), setup drafts (`setup-draft.json`, 7-day expiry).
- `files.*` path contract (both hosts): absolute paths used as-is; relative paths resolve under the workspace root. `files.list` returns `dir`-prefixed relative paths.
- Secrets via HostPort only (`secretRef`).

## 6. Known gaps

- `EngineTurn.hostTools` carries the session tools (`delegate`, `health_report`, `plan_write`, `milestone_done`, `load_skill`, `ask_user`): the native loop merges them into its registry; the `claude-code` engine serves them over a per-turn MCP streamable-HTTP server on 127.0.0.1 (random port + bearer token, `modules/engines/src/mcp.ts`; JSON-RPC `initialize`/`tools/list`/`tools/call`) with `--mcp-config` + `--allowedTools mcp__stewart__*`; tools with `requiresApproval` (e.g. `set_check`) go through `turn.approve` inside the MCP server before they run. Children get no `hostTools` (depth 1).
- Compaction (`session/compact.ts`): before each lead turn and, under native-loop, before every model request (`beforeModelTurn`), when the transcript is estimated (4 chars/token) past 60% of the agent's window (32k when unknown), one range is summarised by one plain request to that agent and replaced by a `[Summary of earlier conversation] #<chunk>` user message: everything before the last two user turns, or — inside one long turn — the work between the open task and the last ≤8 messages (cut at an assistant message), only when that range is at least half the estimate. The removed messages are appended to `<stateDir>/sessions/<id>.archive.jsonl` as `{chunk, message}` first; `history.load` (`fullHistory`) expands summaries back, so the user sees the full transcript. A failed or empty summary leaves the transcript untouched. The active plan rides in the system prompt; the open task stays verbatim. Skipped for `claude-cli` agents (the CLI manages its own context).
- ACP (§7 of the design): not built; see `docs/NEW_DESIGN_2026-11-12.md` §8.1 #11.
- Claude CLI `chat()` is intentionally unsupported (claude-code engine owns that transport); listModels/loginStatus/probeCaps remain for setup.
