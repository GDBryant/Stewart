## 1. Layout

```
packages/
  protocol/    JSON-RPC types, PROTOCOL_VERSION, capability negotiation (src/index.ts)
  core/        all logic; no host imports
  sidecar/     Node stdio JSON-RPC server for JetBrains (rpc.ts, server.ts, host.ts reverse-RPC → HostPort, debugSink.ts)
  webview/     Preact chat + settings + setup wizard, one bundle for both hosts
  evals/       outcome eval suite: fixture repo, code-scored tasks, Node HostPort runner over a real Core (docs/ai_docs/EVALS.md)
modules/       17 `@stewart/<module>` packages, each with a `README.md` (purpose, surface, owns, deps). Modules import only strictly lower layers (`scripts/layers.json`, `pnpm check:layers`); every package is `composite` with a 90/80 coverage gate. Product version 3.0.0 (`hosts/vscode/package.json`, `build.gradle.kts`). Layers: see table in §1a.
hosts/
  vscode/      in-process core; host.ts implements HostPort via vscode API; routes.ts = webview message route table + dispatchAndReply
  jetbrains/   Kotlin: SidecarSupervisor (bundled Node, restart/backoff), HostRequestHandler, JCEF WebviewRouter
```

```
webview ─postMessage─ host ─(in-process | stdio NDJSON JSON-RPC)─ Core.dispatch
                                                                    │
                                                 ConfigStore    ChannelService   SessionService ─→ Engine
                                                 (YAML, schema) (adapters)       (lead turns)      ├ native-loop ─→ channel.chat
                                                                                                   └ claude-code ─→ Claude Code CLI
```

## 3. Run paths

There is exactly one chat path: the lead session.

### 3a. Lead path

`handleChatSend` (no `/direct`, no orchestrated path, no classifier) resolves the enabled `lead` role and calls `ProjectCtx.sessions.send`. `SessionService` (`@stewart/session`) loads the `ChatHistoryStore` transcript + `<stateDir>/sessions/<id>.engine.json`, appends the user message, resolves the lead's **eligible chain** — `eligibleChain` (roles-skills `chain.ts`): `role.chain` else `[role.agent]` else the lead's chain (for lead: the first agent); only agents `agentRefusal` accepts (current passing `qualified[kind]` record — `version < QUAL_MIN_VERSION` refuses "qualification out of date"; window ≥ `needs.minContext` from `contextTokens` or the record's verified `context` — an unknown window is refused "context window unknown"; vision when needed), in chain order; empty → failed "no qualified agent for role <id>: run Qualify in settings" — builds the system prompt (lead prompt + one-line skill index + `loadProjectContext` cut to 8000 chars) and tools (`projectTools(...).for(lead)` + `load_skill` + `ask_user` via `interaction.questionPrompt` + `delegate` + `health_report` + `set_check` + plan tools), then runs `engineFor(channel type)` — `claude-code` for `claude-cli` channels, `native-loop` for everything else. `maxTurns` = `lead.turnBudget` (`unlimited` → 200).

The session emits `run.started`, `text_delta`/`reasoning_delta`, `tool.request`/`tool.outcome` (roleId `lead`); approvals route through `policyApprove(lead, permissions.gate)` (`modules/session/src/policyApprove.ts`) — one `decide(role, actionOf(preview))` before the user-facing gate, so the same role policy applies under both engines — so `chat.approve`/`chat.answer` keep working; usage meters into `RunLedger` (role `lead`) with `cost.summary` when cost > 0 and abort + failed "cost cap reached" past `costLimit.perRunUsd`. At turn start it takes a change-tracker baseline (`begin("turn-<runId>")`, persisted to `<stateDir>/sessions/<id>.turn` so `chat.revert` with `"turn"` restores it — the webview shows a "Revert this turn" action on a failed run's outcome line). After the engine stops it diffs that baseline and runs `runCheck` on `declaredCheck(set_check)` — failed last write records not seen in the diff, declared files that must exist, the commands in the task contract (`set_check({command, files?})` — approved at declaration; `.stewart/project.yaml` `verify:` argv lists — gated like any command and run only when the tracker diff is non-empty or unknown; must exit 0), empty reply — emits `check.result` (evidence details on the wire), and finishes `done` only when the engine stopped normally **and** the check passed; the lead's reply is not citation-checked (it may name files that do not exist yet). Each contract command runs once per attempt; the last attempt's check result is the result (`cancelled` on cancel, else `failed` with the engine error or failing check details). `run.finished` on `done` and `failed` carries `outcome {changed: string[], verified: "command"\|"files"\|"none", command?, tracking?: "unavailable", trackingReason?}` — `changed` is the tracker diff (shell-only edits count, in or out of git), `verified` names what confirmed the result (all contract commands ran and passed — `command` lists them joined with `; ` — else declared files present, else none); the webview shows it as one status line ("No files changed", "Changed N files, not verified", "Changed N files; verified: <command>", "Changed N files; required files present", or "File changes not tracked: <reason>"). Transcript + engine state persist incrementally (`stepSaver`, a single-flight coalescer): once right after the user message is appended (before the engine starts), once coalesced after every `tool.outcome`/`finished` engine event (`TaskSpec.onStep` — at most one save in flight, steps that arrive meanwhile coalesce into exactly one more save that reads the live transcript, so a post-compaction save can never be overwritten by pre-compaction state), and at task end/after each milestone. Save failures log and never fail the run. On load `closeOpenCalls` repairs a transcript interrupted mid tool batch (each unanswered call of the last open batch gets a `tool` message `Interrupted: the session ended before this call finished`); a trailing user message is left alone. Child transcripts persist the same way to `<stateDir>/sessions/<sessionId>/<taskId>.json`. `chat.cancel` → `sessions.cancel`. Turns on one session serialize.

**Escalation over the chain.** Each attempt runs the next eligible agent. A failed attempt — check failure, engine error, `turn_limit`, `loop_guard` — escalates: a handover user message is appended (`Handover: the previous agent (<id>) did not finish this task. Goal: … Tried: … Failing evidence: … Continue from the current state of the files.`), `run.escalated {from,to,reason}` is emitted (reason `check_failed`|`error`|`turn_limit`|`loop_guard`), and writes/changed-file records accumulate so the final check covers all attempts. "Tried" outcomes are matched to calls by `callId`. No escalation on cancel or cost cap. After the last agent fails the session asks via `ask_user` ("All agents for this task failed. … retry once more on <lastAgentId>, or stop.", options `["Stop"]`): any other answer retries that agent once with the guidance appended; `Stop`/timeout fails with the evidence. Delegated children escalate along their own role chain identically but never ask the user — they return `status: failed` to the lead.

### 3b. Engines

`native-loop` (`engines/nativeLoop.ts`): per model turn `channel.chat` with native `tools` (no text shim), streams text/reasoning/usage, appends assistant/tool messages to the transcript, executes calls sequentially — consecutive calls on tools flagged `parallel: true` run concurrently via `Promise.all`, preserving tool-message order — (validate → preview → `approve` → 120 s timeout — skipped for `awaitsUser` tools (`ask_user`, `plan_write`) and `noTimeout` tools (`delegate`) — 20k-char 70/30 cap, image results pushed as user image messages), emits `write` records for WriteFile/EditFile/ApplyPatch, finishes `stop`/`turn_limit`/`cancelled`/`error`/`loop_guard`. `beforeModelTurn` (session: compaction) runs before every model request. The loop guard (`engines/loopGuard.ts`, also used by `claude-code`) trips when the same call (tool name + canonical JSON args) fails twice in one run, when the same call returns the same result three times, or after 6 consecutive model turns where every call failed or was invalid — the session treats it like `turn_limit` (escalates).

`claude-code` (`engines/claudeCode.ts`/`claudeLines.ts`) spawns the Claude Code CLI as a full agent in the project root: `claude -p --input-format stream-json --output-format stream-json --verbose --permission-prompt-tool stdio --include-partial-messages --model <normalizeModel(agent.model)>` plus `--append-system-prompt` (non-empty system only), `--max-turns`, and `--resume <state.cliSessionId>` when stored. It uses the CLI's own tools — `turn.tools` is ignored — under `claudeChildEnv` (host env minus `ANTHROPIC_API_KEY`/`ANTHROPIC_AUTH_TOKEN`, `MCP_TOOL_TIMEOUT` defaulted to 6 h because Stewart's MCP tools wait on approvals, plan approval and child runs, plus `cfg.extraEnv`). The last user message goes to stdin as one stream-json line (images as base64 blocks); stdin stays open for control traffic, closed after `result`. `can_use_tool` control requests route through `turn.approve` (session-wrapped by `policyApprove`, so role policy applies to the claude-code lead and children alike — enforcement is only as good as the CLI sending `can_use_tool` for every mutating tool) with a mapped preview (meta `roleId` = `turn.roleId`). Every spawn carries `--setting-sources <cfg.settingSources>` (default `""`: no user/project/local settings are loaded, so user CLI `permissions.allow` rules cannot pre-approve a tool without a `can_use_tool` request — the trade-off is that user CLI settings such as hooks and env are not loaded unless the channel sets `settingSources`, which re-opens that pre-approval). Context sync: `state.cliSeen` counts transcript messages the CLI session has seen; at run start, messages before the final user message it has not seen (other-engine turns, handovers, or everything after a compaction) are prefixed to the user line as a `Earlier in this conversation (not yet seen by you):` recap (role-labelled, `[tool <name>]` calls, 300-char tool results, tail-biased 12k cap), and `cliSeen = transcript.length` after the run; the stale-`--resume` retry reuses the same recap. In reverse, the native loop's `forNative` flattens assistant messages containing calls to tools it lacks (other-engine calls) into plain text and drops their tool messages. `claudeCode.complete` spawns `claude -p --output-format json --tools "" --json-schema <schema>` — `structured_output` when present, else the `result` text parsed as JSON (one fenced block allowed), validated by the same `validateArgs`; `is_error` → not ok (Edit/Write/MultiEdit/NotebookEdit → file preview relativised to cwd, Bash → command, others → `OTHER`); other control subtypes get an error response. Deltas dedupe by `api_message_id`; `tool_use`/`tool_result` → `tool.request`/`tool.outcome` + `write` records from `tool_use_result.filePath`; `system.init.session_id` → `state.cliSessionId`; `result` → `usage` (input+cache tokens, `total_cost_usd`) then `finished` (`error_max_turns` → `turn_limit`). Cancel → `interrupt` control_request then kill tree after 3 s. Each `tool_result` feeds a `LoopGuard`; a trip sends `interrupt`, kills the CLI and finishes `loop_guard`. Exit without `result` → stderr tail via `classify` (auth → "Claude CLI not logged in"). Stale `--resume` clears the id and retries once with the same unseen-message recap. Verbatim stream-json captures in `modules/engines/test/fixtures/`.

### 3c. Qualification (`@stewart/setup` `conformance.ts` + `conformanceClaude.ts`, `CONFORMANCE_VERSION = 2`)

Two suites write `Qual {passed, at, version, detail?, context?}` records into `channels.yaml` `modelCaps.<model>.qualified` (same write path as bench `perf`). **Agent suite**: refused without running when `tools === "none"` or a known context < 32000. For `claude-cli` channels the agent suite is a real `claude-code` engine turn in a per-run scratch dir (`<stateDir>/qualify/<uuid>`): `notes/todo.txt` is seeded, the same prompt runs with an empty `ToolRegistry`, `maxTurns` 8, 180 s, and an approve that allows file previews inside the dir, `wc ` commands and read-only calls (everything else is rejected with a hint); wc success is tracked from `tool.request`/`tool.outcome` events; scratch files are deleted afterwards. Other channels run one `nativeLoop` turn against an in-memory sandbox (`notes/todo.txt` = "alpha\nbeta\n"; ReadFile/EditFile/WriteFile/RunTerminal; fake proc where only `wc -l` works, printing `3 notes/todo.txt`; auto-approve; maxTurns 8; 120 s): pass iff the file is exactly `alpha\nbeta\ngamma\n`, a `wc` RunTerminal call succeeded, and the reply contains `3`; detail names the first failed criterion. After either agent suite passes, the record's `context` is the model's known window; when unknown, a **window probe** runs first — one no-tools request whose ≈84,000-char message (≈28k real tokens: numbered filler lines) asks for the code word on its first line, sent over `channel.chat` for text channels or one `claude-code` engine turn for `claude-cli` — pass iff no error, not truncated, the word is echoed, and reported input usage (when present) is ≥ 20k; the pass records `context: 32000` (a verified 32k-class window), failure refuses "context window below 32000". **Function suite**: one plain request; the reply (optionally one ```json fence) must parse to `{"sum": 42, "word": "trawets"}`. Triggers: the wizard probe qualifies each green candidate inline (results land on `SetupProbeItem.qualified` and persist on `setup.approve`), and `setup.qualify {channel, model}` (Settings "Qualify" button) runs and persists immediately. `scoreAssignments` refuses candidates without a passing record for the role's `kind` (missing counts as not qualified) or failing its `needs` (vision, `minContext` default 32000 for agents), and proposes `chain` (qualified candidates, free/local then cheapest, claude-cli last, max 3) on each assignment. The AI-refine path applies the same role `kind`/`needs` (`hardRefusal` with role meta) and refuses never-probed models. `roles.assignAgent` refuses an agent the lead refuses; Settings role pickers list only qualified agents (plus vision when needed); saved roles are validated (`chainErrors`) so any refused bound/chain agent is a config error. Probe tool modes are `native` / `none` / `unknown` (v2 `shim` loads as `unknown`).

### 3d. Setup bench probe

`channel.probe --bench` (`packages/core/src/probeLoop.ts`) runs `nativeLoop` with one synthetic tool and an auto-approve gate; it aborts the turn the moment the probed tool's outcome arrives, so `toolReliability`/`editOk` measure "did the model issue a valid native call" in one round trip; `jsonOk` comes from a plain chat probe. Unknown measurements warn instead of hard-failing recommendations.

### 3e. Long builds (plans, milestones, checkpoints)

Lead-only tool `plan_write({goal, milestones:[{title, detail?, check:{command?: string[], files?: string[]}}]})` (`modules/session/src/plan.ts`, `PlanRunner`) validates every milestone has a `check.command` argv or `check.files`, then asks once via `ask_user` "Approve this plan?" — approval of the plan approves its check commands. Approve → baseline `tracker.begin("start")` (id persisted at `<stateDir>/sessions/<id>.plan`), the plan saved `active` at `.stewart/plans/<sessionId>.md` (`@stewart/tasks` `renderPlan`/`parsePlan`, argv rendered as a JSON array — a legacy backticked string parses as `["sh","-c",<str>]`), `plan.approved`. The session then **drives** the plan (`SessionService.drive`): after the lead task that approved it finishes `done`, each pending milestone runs as its own lead `runTask` of the same run — a `Milestone <id> of <n>` user message is appended (`milestone.started`), `plan_write` is not offered, `set_check` is reset, the contract is the milestone check (approved) + project verify + that task's `set_check`, `mustChange` applies to files-only milestones, and the baseline is the last done milestone's checkpoint (plan baseline for the first). Done → `tracker.begin("<id>")` is the milestone checkpoint + `milestone.done`; all done → plan `done`. Failed after the chain (and the interactive retry) → milestone `failed`, plan `paused`, `milestone.failed`, run fails `milestone <id> failed: <text>`; cancel/cost-cap → plan `paused`, milestone stays pending. A non-done lead task pauses an active plan; a normal turn on a paused plan does not drive it. Transcript and plan file persist after every milestone; one `run.started`/`run.finished` per run, outcome `changed` = diff of the run's first baseline. An unfinished plan rides in the lead system prompt (`# Plan (<status>)`, ≤4000 chars). `chat.resume` starts a driver-only run (`Resume plan: <goal>` — a failed current milestone resets to pending); `chat.revert` restores `"turn"`, a named/latest/"baseline" checkpoint via `tracker.restore`, resets milestones after it to pending and pauses the plan, and emits `run.reverted`. `history.load` returns a `plan` summary; the webview shows a plan card with per-milestone Revert buttons and a Resume-plan action.

### 3f. Delegation

`delegate({role, task, report?, check?, schema?})` (lead only, `parallel: true`, `noTimeout`; the lead prompt limits it to read-only parallel work, reading that would flood the lead's context, and narrow checkable work for a cheaper qualified role; `check = {files?, command?}` is verified by code after the child stops, the command goes through the approval gate — refusal is `command_denied` check evidence) runs a child turn through the same `runTask` path (contract = `delegate` check + `.stewart/project.yaml` `verify:` for write-capable roles; `interactive: false`): agent = `role.agent` else the lead's resolved agent; engine via `engineFor` (same engine id, incl. `claude-code`); tools = `projectTools(...).for(role)` + `load_skill` (children never get `delegate`/`health_report` — depth 1); system = role prompt + skill index + project notes; transcript = the task as one user message; `maxTurns` = `role.turnBudget`; up to 4 children run concurrently, but children whose role has write tools (and are not `kind: function`) run behind a FIFO read/write lock: a waiting writer blocks later readers and holds while readers finish; readers share (function tasks take no lock). A `kind: function` role takes `schema` (JSON Schema object) and runs `engine.complete` per qualified `function` agent in chain order (no tools, no transcript — native channels carry `responseSchema`, OpenAI `response_format: {type: "json_schema"}` / Ollama `format`, retried once without it on a 4xx rejection; `claude-cli` agents run one `claude -p --json-schema` turn; a reply that is not a schema-valid JSON object escalates to the next agent); the delegate result is `status: done` + the JSON. Read-only roles (no write tools) get the generic read-only terminal guard; every child's approve is `policyApprove(role, gate)` — the same `decide` before-the-fact rule for native tools and `claude-code` `can_use_tool` previews (file edits need a project path not in `.git/`/`.stewart/` (`.stewart/scratch/` allowed) and matching `writePaths`, commands need `RunTerminal` and the read-only allow-list for read-only roles). Under `claude-code` before-the-fact enforcement depends on the CLI sending `can_use_tool`; a restricted-role **policy backstop** catches what slips past after the fact: at verify time every path in the tracker diff must pass `decide(role, {kind:'write'})`, each failure emits `policy_violation` evidence (`changed outside role policy: <path> (<reason>)`, capped at 10 paths + "and N more") and the task fails — no auto-revert. Unrestricted roles (the default lead) are not backstopped, and `.git/`/`.stewart/` changes are outside the tracker's view by design. Each child takes its own `tracker.begin("task-<taskId>")` baseline at start and diffs it at check time (the shared tracker serializes calls); a parallel read-only child's diff can only contain the lead's own output, which is nothing while the lead is blocked in `delegate` — no special handling. Write records feed the lead's plan and the `write_failed` rule only. Each child's check is its `delegate` `check` ({files?, command?}) plus `cites: true` and `needsRead: true` for read-only roles (every cited path:line must exist, and the child must have made at least one successful read) and, for `report: "health"`, `schema: "health"` (exactly one ```json block validating as `HealthReport`, all report paths must exist). Status is `done` iff engine stop + check passed; the delegate result text is `status: <s>` + the reply (8k cap) + `check: <evidence>` on failure — a failed child is a tool success, not an error. Events: `task.created`/`task.started`/`task.done`/`task.failed` with `taskId`+`roleId`; child text/tool rows carry `taskId`; usage meters to the ledger under the child role and counts toward the run cost cap. Child transcripts save to `<stateDir>/sessions/<sessionId>/<taskId>.json` (not in the history list). `health_report()` merges successful `report:"health"` children via `@stewart/code-health` (`mergeReports` + `aggregate` + `renderReport("issues", ...)` + `scanMetrics`/`summarizeMetrics`), writes `.stewart/reports/health-<runId>.md` through the host, returns the rendered text + path; fails "no health reports in this run" when empty. Shipped roles: `lead`, `explorer` (read-only search), `reviewer` (read-only review), `planner` (read-only; returns milestones with checks), `tester` (writes only test paths, runs them); `project-health` skill on the lead orchestrates batched reviewer runs.

## 4. Model facts

Per `channel/model`, facts come from: `modelCaps` in `channels.yaml` (user, wins — includes `qualified` records) ← probe cache (in-memory) ← bench `perf` ← catalog / live `priceList`; agent `price` wins for cost. `models/profile.ts` is the single merge; raw `modelCaps` reads go through `userCaps`/`capsFor` (`check:boundaries` forbids raw reads outside the allowlist).

## 5. Config and state

- Files: shared `~/.config/stewart/{channels,agents,roles,settings}.yaml`, `skills/` — one dir for every IDE and project (`@stewart/config` `userDir.ts`; Kotlin mirror `UserConfigDir.kt`). Created on host start. Files must be `.yaml`; project `.stewart/{roles.yaml,project.yaml,skills/}` (trusted workspaces only; `project.yaml` `verify:` = list of argv arrays run as contract commands on every write-capable task). Old keys (budgets, recovery, lease/plan settings, `fallbackAgent`) parse and are ignored. Role fields: `kind` (`agent` | `function`, default agent), `needs` (`vision`, `minContext` — agent default 32000), `chain` (agent ids, cheapest first); `agent` alone still works.
- Child transcripts live at `<stateDir>/sessions/<sessionId>/<taskId>.json`; health reports at `.stewart/reports/health-<runId>.md`; plans at `.stewart/plans/<sessionId>.md`; the persistent temp git index at `<stateDir>/checkpoints/<sessionId>.index`, manifest baselines (`base-<n>.json`) and content-addressed blobs under `<stateDir>/checkpoints/<sessionId>/`; checkpoint commits under `refs/stewart/<sessionId>`; plan baseline id at `<stateDir>/sessions/<sessionId>.plan`; last turn baseline id at `<stateDir>/sessions/<sessionId>.turn`.
- State dir (HostPort): `ledger.jsonl`, `sessions/<id>.engine.json`, chat history (`ChatHistoryStore`, owned by `@stewart/session`), setup drafts (`setup-draft.json`, 7-day expiry).
- Session deletion (history retention prune past `historyRetentionDays` and explicit `history.delete` share `ChatHistoryStore.delete`, which calls back into `SessionService.dropSessionArtifacts`) removes, per session: `sessions/<id>.{engine.json,turn,plan,archive.jsonl}`, the child-transcript dir `sessions/<id>/`, `.stewart/plans/<id>.md`, and `tracker.dispose()` — `<stateDir>/checkpoints/<id>/` (manifests + blobs), `<id>.index`, and `git update-ref -d refs/stewart/<id>` (failure ignored). The in-memory per-session turn chain map drops its entry once a turn settles and no newer turn replaced it.
- `files.*` path contract (both hosts): absolute paths used as-is; relative paths resolve under the workspace root. `files.list` returns `dir`-prefixed relative paths.
- Secrets via HostPort only (`secretRef`).

## 6. Known gaps

- `EngineTurn.hostTools` carries the session tools (`delegate`, `health_report`, `plan_write`, `load_skill`, `ask_user`, `set_check`): the native loop merges them into its registry; the `claude-code` engine serves them over a per-turn MCP streamable-HTTP server on 127.0.0.1 (random port + bearer token, `modules/engines/src/mcp.ts`; JSON-RPC `initialize`/`tools/list`/`tools/call`) with `--mcp-config` + `--allowedTools mcp__stewart__*`; tools with `requiresApproval` (e.g. `set_check`) go through `turn.approve` inside the MCP server before they run. Children get no `hostTools` (depth 1).
- Compaction (`session/compact.ts`): before each lead turn and, before every model request when `engine.caps.ownContext` is false (`beforeModelTurn`), when the transcript is estimated (4 chars/token) past 60% of the agent's window (32k when unknown), one range is summarised by one plain request to that agent and replaced by a `[Summary of earlier conversation] #<chunk>` user message: everything before the last two user turns, or — inside one long turn — the work between the open task and the last ≤8 messages (cut at an assistant message), only when that range is at least half the estimate. The removed messages are appended to `<stateDir>/sessions/<id>.archive.jsonl` as `{chunk, message}` first; `history.load` (`fullHistory`) expands summaries back, so the user sees the full transcript. A failed or empty summary leaves the transcript untouched. The active plan rides in the system prompt; the open task stays verbatim. Skipped when the engine owns context (claude-code).
- ACP (§7 of the design): not built; see `docs/NEW_DESIGN_2026-11-12.md` §8.1 #11.
- Claude CLI `chat()` is intentionally unsupported (claude-code engine owns that transport); listModels/loginStatus/probeCaps remain for setup.
