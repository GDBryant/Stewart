1. The big one. I noticed the bit in your design doc about 39 runs over 7 days with no file changes. We had almost exactly that and I spent a full day rewriting tasks that turned out to be completely fine. What it actually was, every gate we had was grading what the model produced, and nothing was grading what the harness was handing it. We replayed 202 tool calls back through our policy engine and 32% came back dead, refused or crashed, so the model was working blind the whole time. If you haven't already checked that angle, taking one failing run and counting how many tool calls came back usable might be worth an hour. It was free for us and it was the whole answer.

2. Command grants. Ours prompted on anything the shell parser couldn't handle, same as yours, and it was quietly refusing 52% of all shell calls.  It was blocking dangerous stuff, when it was only blocking the two command spelling, the one liner went straight through. We carved out reads and searches and it dropped to 35% with nothing nasty getting past it. Worth measuring the actual rate rather than going off how many prompts you see.

3. Windows. We lost 36 of 202 calls to processes that just never started, 0xC0000142. Ended up being stdin=DEVNULL on every spawn plus a retry. Your sidecar supervisor, the claude -p spawn and the per turn MCP server are the places I'd look first. It presents as a hang that looks identical to a model problem, which is what made it take so long to find.

Related to that, we were letting raw exit codes reach the model. exit code 3221225794 means nothing to it and it can't recover, so the turn is just dead. Making failed tools report a cause instead was a small change with a big effect.

4. Evals, this one is less a warning and more a thing I got caught by. We scored ourselves on a suite we wrote and sat at full marks for ages, which turned out to be measuring the suite. We moved to SWE-bench Verified scored per instance. If you ever go that way, the trap that cost me a day is that django instance ids are unittest labels and sympy's are bare function names, so roughly 244 of the 500 need a resolver and a plain pytest run fails every one of them no matter how good the work was.

5. Last one, letting claude-code own its own context. Makes complete sense and we do something similar, but it did mean we couldn't tell a context failure from a model failure on the path we cared about most. We ended up splitting it, a chat compresses and a build hands over to a fresh generation, because they turned out to be different problems.
