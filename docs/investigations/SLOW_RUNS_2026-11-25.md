# Slow runs investigation, 2026-11-25

Source: `~/.cache/JetBrains/PyCharm2026.3/log/stewart/debug_logs/2026-11-25.log` (771 model requests, 6 runs, 07:17–~14:00 UTC, project Stewart).
Only this day was analysed. `2026-11-24.log` (725 MB) was not. Scripts were throwaway and are not kept.

## Setup in the log
- Lead role runs on `AIF-qwen3-8-27b` (channel `AIF`, openai-compatible, an Azure-hosted proxy, `effort: medium`). Secondary is `claude-sonnet`. Escalation never fired.
- `channels.yaml` records the qualified context as **32000** tokens for this model.

## Where the time goes
Run-7 ("Build in all the fixes listed") is the big one: 8046 s wall, 660 requests, 6607 s (82%) spent waiting on the model. The other runs are 93–99% model time apart from user/approval waits.

| Measure (run-7) | Value |
|---|---|
| Completion tokens | 981,883 |
| of which reasoning tokens | 806,378 (**82%**) |
| Decode rate | ~149 tok/s (981k tokens ÷ 6607 s, so decode accounts for essentially all model time) |
| Avg request | 9.1 s, 1,300 completion tokens |
| Requests that are >80% reasoning | 186 of 607. They account for 4,298 s (65% of model time) |
| Compaction requests | 53, costing 1,057 s (16%) |
| Total prompt tokens sent | 18.1 M |

Tool execution is minor: apart from user/approval gaps, inter-request gaps sum to ~500 s across the whole day. The gaps over 60 s (7,700 s in total) are mostly user or approval waits and idle time between runs, not harness work.

## Causes, ranked by evidence
1. **Reasoning volume (dominant, ~5,400 s).** Roughly 4 of every 5 generated tokens are reasoning, and many tool steps reason for 500–40,000 chars to emit a ~100-token tool call. Examples: a 158 s request with 99k chars of reasoning to return 116 chars of content, and 154 s for 81k chars of reasoning. Prefill is negligible next to decode. `effort: medium` does not bound this on this model.
2. **Compaction thrash (~1,057 s, plus knock-on cost).** Compaction fires once the estimate passes 60% of the 32k window (~19k tokens), but real prompts run up to 55k tokens: 211 of 607 requests exceed 32k, and the prompt before a compaction ranged 22k–46k. Compaction fired every 2–33 requests, with a median of ~12 and several runs of 2–3. Each pass is a model call of ~20 s. After it, the context loses file contents, so the agent re-reads them: `StewartProjectService.kt` 26×, `NodeFetcher.kt` 24×, `SidecarSupervisor.kt` 23×, `StewartToolWindowFactory.kt` 23×, `NodeLocator.kt` 22×. The compaction rule ("last ≤8 messages kept, range must be ≥ half the estimate") cannot get under the threshold when a few large tool results sit in the kept tail. The 20k-char tool-result cap is generous relative to a 32k window.
3. **Exploratory shell loops.** About 400 `RunTerminal` calls, ~120 of them probing `~/.gradle/caches/.../transformed/idea-2026.1` jars (`unzip -l` over every jar looking for a class). Each costs a reasoning-heavy model turn before and after it. The task needed a Balloon API check, not a jar sweep. This is a prompt/policy gap, not a bug.
4. **Long single runs.** 660 requests in one run, with 18 M prompt tokens re-sent. No prompt cache information is returned (`prompt_tokens_details: null`), so cached-prefix savings are unknown.

## Not the cause
- Network or HTTP errors: no `error`-direction lines in this day's log.
- Tool timeouts or approvals inside runs: few; the large gaps are between runs.
- Loop guard: never tripped.

## Caveats
Streamed chunks are logged with almost identical timestamps at request completion, so time-to-first-token and prefill cannot be separated from decode. The 149 tok/s figure is the blended rate. Compaction cost excludes the extra re-reads it causes, which I only counted, not timed.

## Suggested actions (not implemented)
1. Cap reasoning for this channel: send a reasoning-effort/`reasoning_budget` or a `/no_think`-style switch for tool-routine turns, or default this agent to `think: false` for the lead role with escalation to a reasoning agent only on stall.
2. Fix compaction for small windows: base the threshold on measured `prompt_tokens` from the last response rather than the 4 chars/token estimate. Compact the retained tail too (truncate old tool results in place). Set a hysteresis target so one pass leaves headroom (e.g. down to 40%).
3. Lower the per-tool-result cap for windows ≤32k, and stop re-reading files already summarised (keep a short "files read" digest in the summary).
4. Use a larger-window agent as the lead for long build runs, or let the 32000 qualified context be re-probed; the model may support more than recorded.
5. Add a system-prompt nudge against whole-cache jar sweeps, or a tool for symbol lookup.
